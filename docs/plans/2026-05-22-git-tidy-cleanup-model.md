# git-tidy 정리 모델 재설계

본 문서는 git-tidy 가 로컬 브랜치를 정리 대상으로 판단하는 모델의 설계를 담는다.
구현 작업은 이 설계를 단일 기준으로 삼는다.

## 한 줄 정의

git-tidy 는 로컬 git 브랜치를 일괄 정리하는 zsh 플러그인이다. 작업이 끝났거나 오래
방치된 브랜치를 자동으로 찾아 보여주고, 사용자가 확인하면 한 번에 삭제한다.

## 정리 모델 — 하이브리드

git-tidy 가 한 브랜치를 삭제 대상으로 판단하는 규칙은 두 층으로 이뤄진다.

- **삭제 후보 신호**: 그 브랜치의 작업이 끝났거나 낡았다는 것을 가리키는 양성 신호다.
  세 신호 중 하나라도 해당하면 그 브랜치는 삭제 후보가 된다.
- **보호 규칙**: 후보로 잡혔더라도 절대 삭제하면 안 되는 구조적 조건이다. 하나라도
  해당하면 후보에서 도로 제외한다.

최종 삭제 대상은 삭제 후보 신호에 걸렸고 보호 규칙에는 걸리지 않은 브랜치다.

두 층을 모두 두는 이유가 있다. 보호 규칙만으로 정리 범위를 정하면(보호되지 않은
브랜치를 전부 삭제하는 방식) 보호 목록이 조금만 부실해도 아직 쓰는 브랜치까지
지운다. 반대로 삭제 후보 신호만 두면 현재 체크아웃된 브랜치처럼 절대 건드리면 안
되는 것을 막을 마지막 수단이 없다. 삭제하려면 작업이 끝났다는 양성 근거가 있어야
하고, 그 위에 구조적 안전장치를 한 겹 더 얹는 구성이 양쪽의 약점을 함께 막는다.

## 삭제 후보 신호

브랜치가 다음 세 신호 중 하나라도 해당하면 삭제 후보다.

1. **`[gone]`** — upstream 추적 브랜치가 사라진 경우다. `git for-each-ref` 의
   `%(upstream:track)` 값이 `[gone]` 으로 나오는 브랜치이며, 보통 원격에서 PR 이
   머지된 뒤 원격 브랜치가 삭제되면 이 상태가 된다. squash merge 워크플로에서
   작업이 끝났다는 것을 가장 신뢰성 있게 알려주는 신호다.

2. **merged** — 브랜치의 커밋이 base 브랜치에 모두 들어간 경우다.
   `git branch --merged <base>` 로 감지한다. 이 방식은 fast-forward 나 merge commit
   으로 합쳐진 브랜치는 잡지만, squash merge 로 합쳐진 브랜치는 커밋이 새로
   만들어져 reachability 가 끊기므로 잡지 못한다. squash merge 경우는 위의 `[gone]`
   신호가 대신 담당하므로, 두 신호가 서로의 빈틈을 메운다.

3. **stale** — 브랜치가 오래 방치된 경우다. 다음 둘 중 하나라도 참이면 stale 로
   본다.
   - 브랜치의 마지막 커밋이 stale 판정 창(기본 20일)보다 오래됐다.
   - 브랜치가 base 와 갈라진 지점(merge-base)의 커밋이 stale 판정 창보다 오래됐다.

   한 번도 push 하지 않은 순수 로컬 브랜치도 마지막 커밋이 오래되면 이 신호로
   잡힌다. 따라서 `[gone]` 신호가 못 잡는 미푸시 브랜치가 stale 에서 정리된다.

## 보호 규칙

후보로 잡혔더라도 다음 중 하나라도 해당하면 삭제하지 않는다.

1. **현재 브랜치** — 지금 체크아웃된 브랜치다. 사용자가 작업 중인 위치이며 git 도
   삭제를 거부한다.
2. **base 브랜치** — main, master, trunk 등 자동 감지한 기본 브랜치다. 저장소의
   근간이므로 정리 대상에서 항상 제외한다.

## worktree 에 체크아웃된 브랜치

다른 worktree 에 체크아웃된 브랜치도 삭제 후보가 될 수 있다. worktree 점유는 보호
규칙이 아니다. 이런 브랜치가 삭제 대상이 되면 git-tidy 는 해당 worktree 를
`git worktree remove` 로 먼저 제거한 뒤 브랜치를 삭제한다.

worktree 에 커밋하지 않은 변경이 남아 있으면 `git worktree remove` 가 거부한다.
이때 git-tidy 는 그 브랜치를 "삭제 실패(worktree 정리 안 됨)" 로 보고하고 넘어간다.
미커밋 변경이 있는 worktree 를 강제로 지우지 않는 것이 안전 경계다.

## 명령과 흐름

- `git-tidy` — dry-run 이다. 삭제 대상과 제외된 후보를 표시하고 아무것도 지우지
  않는다. 인자 없는 기본 동작이다.
- `git-tidy --run` — 삭제 대상 목록을 표시한 뒤 `[y/N]` 확인을 받고, 사용자가 `y`
  로 답할 때만 실제로 삭제한다.
- `--stale-days=N` — stale 판정 창을 N일로 바꾼다.
- `--no-fetch` — `git fetch --prune` 단계를 건너뛴다.
- `--version` / `-v`, `--help` / `-h` — 버전과 사용법을 출력한다.
- 별칭 `gtidy` 는 `git-tidy`, `gtidy!` 는 `git-tidy --run` 이다. `--run` 이 항상
  확인 프롬프트를 거치므로 `gtidy!` 도 프롬프트를 띄운다. 확인 스텝은 안전장치이므로
  건너뛰는 경로를 두지 않는다.

dry-run 과 `--run` 을 나누고 `--run` 안에서도 확인을 받는 이유는, 무엇이 지워질지
먼저 눈으로 확인하는 단계와 실제 삭제 직전에 한 번 더 멈추는 단계를 모두 둬서
실수를 이중으로 막기 위함이다.

## 임계값

| 설정 | 기본값 | 환경변수 | 플래그 |
|---|---|---|---|
| stale 판정 창 | 20일 | `GIT_TIDY_STALE_DAYS` | `--stale-days=N` |

최근에 커밋했다는 사실만으로 브랜치를 자동 보호하지는 않는다. 그 판단은 삭제 직전
확인 스텝에 맡긴다. 따라서 최근 커밋 보호 창이라는 별도 설정은 두지 않는다.

## 삭제 수단

삭제는 `git branch -D` 로 한다. `git branch -d` 는 base 에 머지되지 않은 커밋이
있으면 거부하는데, squash merge 로 합쳐졌거나 stale 로 잡힌 브랜치는 `-d` 기준으로는
미머지로 보여 거부당한다. 따라서 `-D` 를 쓰고, 안전은 dry-run 과 `--run` 확인
프롬프트로 보장한다.

## 출력

- **삭제 대상**: 브랜치마다 어떤 후보 신호로 잡혔는지(`[gone]` / merged / stale)
  함께 표시한다. worktree 를 동반 제거해야 하는 브랜치는 그 사실을 함께 표시한다.
- **제외된 후보**: 후보 신호에는 걸렸으나 보호 규칙으로 제외된 브랜치와 그 사유를
  표시한다.
- 후보 신호에 하나도 걸리지 않은 평범한 브랜치는 개별로 나열하지 않고 개수만
  알린다.

## 테스트

재구현된 정리 판단 로직(후보 신호, 보호 규칙, worktree 동반 처리)은 zsh 테스트로
동작을 고정한다. git-tidy 는 순수 zsh 플러그인이라 Go 테스트가 없으므로, zunit
같은 zsh 테스트 프레임워크 도입이 이 도구의 첫 테스트 기반이 된다. zunit 도입과
재구현의 선후 관계는 TDD 원칙(Red 를 먼저 관찰)에 맞춰 구현 계획에서 정한다.

## PRD 갱신 사항

이 설계는 `apps/git-tidy/PRD.md` 와 다음과 같이 어긋나므로, 재구현과 함께 PRD 를
갱신한다.

- PRD 는 보호 규칙이 정리 범위를 결정하는 유일한 수단이라고 적고 있으나, 실제
  모델은 삭제 후보 신호와 보호 규칙 두 층의 하이브리드다. 이 서술을 하이브리드
  모델로 고친다.
- 기능 범위의 `--days=N` 항목을 `--stale-days=N` 으로 바꾸고, 보호 규칙 목록을
  현재 브랜치와 base 브랜치 두 가지로 줄인다.
- 비목표의 "원격 브랜치를 삭제하지 않는다" 는 유지한다. 원격 점검 플래그는 후속
  작업으로 분리한다.

## 범위 밖 — 후속 작업

- **원격 브랜치 점검 플래그**: 로컬 브랜치가 없는 순수 원격 브랜치까지 삭제 검토
  대상에 넣는 opt-in 플래그다. 원격 저장소에 영향을 주는 더 높은 위험이라 이번
  재구현과 분리해 별도로 설계한다.
- **zsh 테스트(zunit) 도입의 상세**: 본 설계는 동작을 zsh 테스트로 고정한다는
  방침만 정한다. 프레임워크 도입과 테스트 작성의 구체 순서는 구현 계획에서 정한다.
