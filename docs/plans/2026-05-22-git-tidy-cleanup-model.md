# git-tidy 재설계 — Go CLI 로 재작성

본 문서는 git-tidy 를 Go CLI 도구로 재작성하는 설계를 담는다. 구현 작업은 이
설계를 단일 기준으로 삼는다.

## 한 줄 정의

git-tidy 는 로컬 git 브랜치를 일괄 정리하는 명령줄 도구다. 작업이 끝났거나 오래
방치된 브랜치를 자동으로 찾아 보여주고, 사용자가 체크박스로 확인하면 한 번에
삭제한다.

## 구현 형태 — Go 바이너리

git-tidy 는 Go 로 작성한 단일 바이너리다. `apps/jg`·`apps/totp` 와 동일하게
`apps/git-tidy/` 아래 `cmd/git-tidy/` 진입점과 `internal/` 패키지로 구성한다.

git-tidy 는 셸의 작업 디렉터리나 환경을 바꾸지 않는다. 브랜치를 삭제하고 결과를
출력할 뿐이다. 따라서 jg·jgw 처럼 셸 함수 wrapper 가 필요 없으며, 사용자는
`git-tidy` 바이너리를 직접 호출한다. 셸 종류(zsh·bash 등)와 무관하게 동일하게
동작하므로, 셸 호환은 설계 문제로 남지 않는다.

git 조작은 `git` CLI 를 `os/exec` 로 호출해 수행한다. 브랜치 목록은
`git for-each-ref --format=…`, worktree 목록은 `git worktree list --porcelain`,
머지 판정은 `git branch --merged`, 삭제는 `git branch -D`, worktree 제거는
`git worktree remove`, 원격 동기화는 `git fetch --prune` 을 쓴다. 이 출력들은
git 이 기계 처리를 위해 안정적으로 유지하는 형식이므로, 그 위에 작은 파서를 두는
것은 본 저장소의 안정성 원칙에 부합한다. jg 가 이미 `git worktree list
--porcelain` 을 같은 방식으로 파싱하고 단위 테스트까지 갖추고 있어 검증된
패턴이다.

## 정리 모델 — 하이브리드

git-tidy 가 한 브랜치를 삭제 대상으로 판단하는 규칙은 두 층으로 이뤄진다.

- **삭제 후보 신호**: 그 브랜치의 작업이 끝났거나 낡았다는 것을 가리키는 양성
  신호다. 세 신호 중 하나라도 해당하면 그 브랜치는 삭제 후보가 된다.
- **보호 규칙**: 후보로 잡혔더라도 절대 삭제하면 안 되는 구조적 조건이다. 하나라도
  해당하면 후보에서 도로 제외한다.

최종 삭제 대상은 삭제 후보 신호에 걸렸고 보호 규칙에는 걸리지 않은 브랜치다.

두 층을 모두 두는 이유가 있다. 보호 규칙만으로 정리 범위를 정하면(보호되지 않은
브랜치를 전부 삭제하는 방식) 보호 목록이 조금만 부실해도 아직 쓰는 브랜치까지
지운다. 반대로 삭제 후보 신호만 두면 현재 체크아웃된 브랜치처럼 절대 건드리면 안
되는 것을 막을 마지막 수단이 없다. 삭제하려면 작업이 끝났다는 양성 근거가 있어야
하고, 그 위에 구조적 안전장치를 한 겹 더 얹는 구성이 양쪽의 약점을 함께 막는다.

## 삭제 후보 신호

브랜치가 다음 세 신호 중 하나라도 해당하면 삭제 후보다.

1. **`[gone]`** — upstream 추적 브랜치가 사라진 경우다. `git for-each-ref` 의
   `%(upstream:track)` 값이 `[gone]` 으로 나오는 브랜치이며, 보통 원격에서 PR 이
   머지된 뒤 원격 브랜치가 삭제되면 이 상태가 된다. squash merge 워크플로에서
   작업이 끝났다는 것을 가장 신뢰성 있게 알려주는 신호다.

2. **merged** — 브랜치의 커밋이 base 브랜치에 모두 들어간 경우다.
   `git branch --merged <base>` 로 감지한다. 이 방식은 fast-forward 나 merge
   commit 으로 합쳐진 브랜치는 잡지만, squash merge 로 합쳐진 브랜치는 커밋이 새로
   만들어져 reachability 가 끊기므로 잡지 못한다. squash merge 경우는 위의
   `[gone]` 신호가 대신 담당하므로, 두 신호가 서로의 빈틈을 메운다.

3. **stale** — 브랜치가 오래 방치된 경우다. 다음 둘 중 하나라도 참이면 stale 로
   본다.
   - 브랜치의 마지막 커밋이 stale 판정 창(기본 20일)보다 오래됐다.
   - 브랜치가 base 와 갈라진 지점(merge-base)의 커밋이 stale 판정 창보다 오래됐다.

   한 번도 push 하지 않은 순수 로컬 브랜치도 마지막 커밋이 오래되면 이 신호로
   잡힌다. 따라서 `[gone]` 신호가 못 잡는 미푸시 브랜치가 stale 에서 정리된다.

## 보호 규칙

후보로 잡혔더라도 다음 중 하나라도 해당하면 삭제하지 않는다.

1. **현재 브랜치** — 지금 체크아웃된 브랜치다. 사용자가 작업 중인 위치이며 git 도
   삭제를 거부한다.
2. **base 브랜치** — main, master, trunk 등 자동 감지한 기본 브랜치다. 저장소의
   근간이므로 정리 대상에서 항상 제외한다.

## worktree 에 체크아웃된 브랜치

다른 worktree 에 체크아웃된 브랜치도 삭제 후보가 될 수 있다. worktree 점유는 보호
규칙이 아니다. 이런 브랜치가 삭제 대상이 되면 git-tidy 는 해당 worktree 를
`git worktree remove` 로 먼저 제거한 뒤 브랜치를 삭제한다.

worktree 에 커밋하지 않은 변경이 남아 있으면 `git worktree remove` 가 거부한다.
이때 git-tidy 는 그 브랜치를 "삭제 실패(worktree 정리 안 됨)" 로 보고하고 넘어간다.
미커밋 변경이 있는 worktree 를 강제로 지우지 않는 것이 안전 경계다.

## 명령과 흐름

- `git-tidy` — dry-run 이다. 삭제 대상과 제외된 후보를 출력하고 아무것도 지우지
  않는다. 인자 없는 기본 동작이다.
- `git-tidy --run` — 삭제 대상을 다중 선택 단계에 띄워, 사용자가 확정한 브랜치만
  삭제한다. 기본은 체크박스 TUI 다.
- `git-tidy --run --no-tui` — 방식 자동 선택을 건너뛰고 줄 기반 선택을 강제한다.
  git-tidy 는 평소 실행 환경을 보고 방식을 자동으로 고르며, 이 플래그는 그 자동
  선택을 덮어쓰는 명시적 override 다.
- `--stale-days=N` — stale 판정 창을 N일로 바꾼다.
- `--no-fetch` — `git fetch --prune` 단계를 건너뛴다.
- `--version` / `-v` — 저장소 표준 형식 `git-tidy v<version> © 2026 silee-tools`
  한 줄을 출력한다.
- `--help` / `-h` — 사용법을 출력한다.
- `gtidy` 와 `gtidy!` 는 `git-tidy` 바이너리를 가리키는 multi-call 단축 명령이다.
  `gtidy` 는 `git-tidy` 와, `gtidy!` 는 `git-tidy --run` 과 같다.

dry-run 과 `--run` 을 나누는 이유는, 무엇이 지워질지 먼저 눈으로 확인하는 단계와
실제 삭제를 확정하는 단계를 분리해 실수를 줄이기 위함이다.

## 확인 단계 — 다중 선택

`git-tidy --run` 은 삭제 대상 브랜치를 사용자가 선택하고 확정하는 단계를 거친다.
선택 방식은 체크박스 TUI 와 줄 기반 선택 두 가지이며, 동작 의미는 같다. git-tidy
가 실행 환경을 보고 방식을 자동으로 고른다.

### 방식 자동 선택

- stdin 이 터미널인지 `golang.org/x/term` 의 `IsTerminal` 로 확인한다. 터미널이
  아니면(출력이 파이프로 연결된 경우, CI 등) 어느 방식도 사용자 입력을 받을 수
  없다. 이때 `--run` 은 터미널이 필요하다는 오류와 함께 종료한다.
- 터미널이고 `TERM` 환경변수가 정상이면 체크박스 TUI 를 쓴다.
- 터미널이지만 `TERM` 이 `dumb` 이거나 비어 있으면, 또는 raw 모드 초기화가
  실패하면 줄 기반 선택으로 자동으로 떨어진다.
- `--no-tui` 를 주면 자동 선택을 건너뛰고 항상 줄 기반 선택을 쓴다. 이 경우에도
  터미널은 여전히 필요하다.

### 체크박스 TUI

- 터미널 raw 모드에서 체크박스 목록을 띄운다. 모든 항목은 처음에 전부 체크된
  상태다.
- 화살표로 항목 이동, 스페이스로 개별 토글, 전용 키로 전체 토글, Enter 로 확정,
  ESC·Ctrl-C 로 취소한다.
- 구현은 `golang.org/x/term` 으로 raw 모드를 켜고 ANSI 이스케이프로 직접
  렌더링한다. 삭제 대상은 평면 목록이라 화면 제어가 단순하고, 무거운 TUI
  프레임워크 없이 작은 코드로 충분하다. bubbletea 계열 프레임워크는 의존이 늘고
  본 저장소에 선례가 없어 채택하지 않는다.

### 줄 기반 선택

- 번호를 매긴 삭제 대상 목록을 출력한다. 모든 항목은 처음에 전부 체크된 상태다.
- 사용자가 번호를 입력하면 그 항목의 체크가 토글되고 목록을 다시 출력한다. 전체
  토글과 취소도 줄 입력으로 받는다.
- 사용자가 완료를 입력하면 체크된 브랜치를 보여주고 최종 `[y/N]` 확인을 받는다.

### 공통 규칙

- 확정하면 체크된 브랜치만 삭제한다. 전부 해제하고 확정하면 아무것도 지우지
  않는다. 취소해도 아무것도 지우지 않는다.
- 비대화형 환경에서 삭제 대상을 보려면 인자 없는 `git-tidy` dry-run 을 쓴다.
  의도치 않은 일괄 삭제를 막기 위해, 비대화형에서 자동으로 전체를 삭제하는 경로는
  두지 않는다.
- 선택 상태(어떤 브랜치가 체크됐는지, 개별 토글과 전체 토글의 결과)는 렌더링·입력
  과 분리한 순수 모델로 둔다. 체크박스 TUI 와 줄 기반 선택이 이 한 모델을
  공유하며, 모델은 단위 테스트로 검증한다.

## 임계값

| 설정 | 기본값 | 환경변수 | 플래그 |
|---|---|---|---|
| stale 판정 창 | 20일 | `GIT_TIDY_STALE_DAYS` | `--stale-days=N` |

최근에 커밋했다는 사실만으로 브랜치를 자동 보호하지는 않는다. 그 판단은 삭제
확정 단계의 체크박스 TUI 에 맡긴다. 따라서 최근 커밋 보호 창이라는 별도 설정은
두지 않는다.

## 삭제 수단

삭제는 `git branch -D` 로 한다. `git branch -d` 는 base 에 머지되지 않은 커밋이
있으면 거부하는데, squash merge 로 합쳐졌거나 stale 로 잡힌 브랜치는 `-d` 기준으로는
미머지로 보여 거부당한다. 따라서 `-D` 를 쓰고, 안전은 dry-run 과 `--run` 의
체크박스 확인으로 보장한다.

## 출력

- **삭제 대상**: 브랜치마다 어떤 후보 신호로 잡혔는지(`[gone]` / merged / stale)
  함께 표시한다. worktree 를 동반 제거해야 하는 브랜치는 그 사실을 함께 표시한다.
- **제외된 후보**: 후보 신호에는 걸렸으나 보호 규칙으로 제외된 브랜치와 그 사유를
  표시한다.
- 후보 신호에 하나도 걸리지 않은 평범한 브랜치는 개별로 나열하지 않고 개수만
  알린다.

## 테스트

정리 판단 로직(후보 신호 분류, 보호 규칙, worktree 분류)과 체크박스 선택 모델은
git 호출·터미널 입출력에서 분리한 순수 함수·구조체로 두고 `go test` 로 단위
테스트한다. git 호출과 터미널 raw 입출력의 실제 경계는 변경 경로 1회성 E2E 로
검증한다. git-tidy 가 Go 도구가 되므로 별도의 zsh 테스트 프레임워크는 도입하지
않는다.

## 저장소 통합 작업

git-tidy 를 Go 도구로 만들면서 다음을 함께 정리한다.

- `apps/git-tidy/` 를 Go 모듈로 구성한다. `.goreleaser.yaml` 의
  `builds: [{skip: true}]` 를 실제 Go 빌드 설정으로 바꾸고, `archives` 의
  `meta: true` 도 일반 바이너리 아카이브로 바꾼다. `.mise.toml` 에 build·test·
  lint 등 Go 태스크를 둔다.
- `completions/_git-tidy`(zsh)·`completions/git-tidy.bash`(bash) 를 둔다.
- 루트 `CLAUDE.md` 의 git-tidy 설명(순수 zsh 플러그인, `builds: skip`, 버전
  conformance 게이트의 zsh 플러그인 분기)을 Go 도구 기준으로 갱신한다.
- homebrew-tap 의 `Formula/git-tidy.rb` 를 바이너리 설치 방식으로 바꾼다.
- roadmap(`docs/plans/2026-05-21-roadmap.md`) 단계 4 의 git-tidy 후속 작업
  서술을 "Go 재작성" 으로 갱신한다. zsh 테스트(zunit) 도입 항목은 사라진다.

## PRD 갱신 사항

`apps/git-tidy/PRD.md` 를 다음과 같이 갱신한다.

- 한 줄 정의의 "zsh 플러그인" 을 "명령줄 도구" 로 바꾼다.
- 정리 모델을 하이브리드(후보 신호 ∩ 보호 규칙 아님)로 다시 쓰고, 후보 신호
  3개·보호 규칙 2개·다중 선택(체크박스 TUI 와 줄 기반 `--no-tui`)·`--stale-days`
  를 반영한다.
- 외부 의존에서 zsh 필수 의존을 뺀다. zsh·bash 는 자동완성용 선택 의존이며 git 은
  필수 의존으로 유지한다.
- 품질 dimension 선언을 Go 도구 기준으로 다시 한다. `test_quality` 는 opt-in 으로
  바뀐다. 셸 통합 관련 dimension 은 git-tidy 가 셸 상태를 바꾸지 않는 순수 CLI
  라는 점을 reason 으로 단다.
- 비목표의 "원격 브랜치를 삭제하지 않는다" 는 유지한다.
