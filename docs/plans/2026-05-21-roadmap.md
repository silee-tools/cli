# silee-tools/cli 도구 품질 정합성 확보 roadmap

본 roadmap 은 jgw 추가에서 시작해 도구 품질 framework 구축까지 이어지는 일련의
작업을 한 곳에서 관찰·실행할 수 있도록 정리한다. 개별 plan 들(`docs/plans/`
아래) 이 각 단계의 상세를 갖고, 본 문서는 그들의 순서·의존·완료 조건을 묶는다.

## 본 roadmap 의 목적

다음 세 가지를 한 흐름으로 시퀀싱한다.

1. `jgw` 형제 명령과 셸 통합 단일 진실 소스 구조의 완성
2. 본 모노레포 전체에 적용될 도구 품질 minimum 기준 framework 의 도입
3. 기존 도구들(jg, totp, git-tidy) 이 그 framework 를 통과하도록 만드는 보정

## 단계 구성과 owner

`사용자` 는 본 저장소의 1인 운영자이며 PR 머지·push·PRD 본문 작성·인터랙티브
검증을 담당한다. `에이전트` 는 plan 에 따라 구현·테스트·문서 갱신을 담당한다.

### 단계 1 — 본 jgw PR 닫기

  `apps/git-tidy/PRD.md` 의 본문과 품질 dimension 선언을 인터뷰로 채웠다. jg 는
  18개 dimension 모두 opt-in, totp 는 shell integration 관련 3개 opt-out,
  git-tidy 는 bash·plugin·test_quality 관련 4개 opt-out 으로 선언됐다. 결과는
  이미 commit 되어 위 "현재 상태" 의 23 commits 에 포함되어 있다.
- **사용자** 1.2 1회성 E2E 5건 검증 — `docs/plans/2026-05-20-jgw.md` 섹션 4 의
  빈 worktree·flowA 2개·flowB 두 단계·header-lines 비활성·preview 갱신 5건을
  실제 git worktree 와 fzf 환경에서 통과시키고, 결과(스크린샷 또는 셸 캡처) 를

- **사용자** 1.3 cli 저장소 push — `cd /Users/silee/repos/silee-tools/cli &&
  git push origin main`. 18 commits + 위 1.1 commits 가 한 번에 push 된다.

- **사용자** 1.4 tap 저장소 push — `cd /Users/silee/repos/silee-tools/homebrew-tap

### 단계 3 — 후속 도구 추가 시 자동 적용

framework 가 안착하면 이후 새 도구(`apps/<new-tool>/`) 가 추가될 때마다 본
roadmap 의 단계 2 가 작은 형태로 반복된다. 신규 도구는 다음을 충족하면 자동으로
품질 검증 대상이 된다.

- **사용자** 새 도구의 PRD 작성(`apps/<new-tool>/PRD.md`) — 본문 + dimension
  선언.
- **에이전트** 새 도구 구현. PRD 의 opt-in dimension 들을 모두 충족.
- **사용자** push. CI 가 18 dimension 을 자동 검증.

완료 조건은 도구별 PRD 의 수용 기준 충족과 framework CI 통과 두 가지의 교집합.

### 단계 4 — PRD 인터뷰에서 드러난 git-tidy 후속 작업

`apps/git-tidy/PRD.md` 작성 인터뷰 과정에서 framework 와 별개의 git-tidy 자체
작업 두 건이 드러났다. 둘 다 단계 2 의 framework 가 git-tidy 를 그린 라이트로
통과시키려면 선행되어야 한다.

- **git-tidy 정리 모델 재구현**: PRD 의 한 줄 정의와 수용 기준은 "보호 규칙으로
  정리에서 제외할 브랜치를 정의하고, 보호되지 않은 나머지 브랜치를 모두 정리 대상으로
  삼는다" 는 모델을 명시한다. 즉 정리 대상을 일부만 골라내는 것이 아니라 보호 규칙이
  정리 범위를 결정하는 유일한 수단이다. 현재 구현은 upstream 이 사라진 `[gone]`
  브랜치만 대상으로 삼으므로 PRD 의 수용 기준을 아직 충족하지 못한다. 보호 규칙 기반
  모델로의 재구현이 필요하다. 이 작업은 정리 대상이 "보호되지 않은 모든 브랜치" 로
  넓어지는 만큼 보호 규칙의 정밀도가 안전성을 좌우하므로, 재구현 전에 보호 규칙의
  정확한 정의(어떤 브랜치를 반드시 보호할지) 를 먼저 합의한다.
- **git-tidy zsh 테스트 도입**: PRD 가 `unit_tests_exist` 와 `tests_execute_and_pass`
  를 opt-in 으로 선언했다. git-tidy 는 순수 zsh 플러그인이므로 zunit 같은 zsh 테스트
  프레임워크를 도입해 두 dimension 을 실제로 충족시켜야 한다.

두 작업의 순서는 재구현이 먼저다. 정리 모델이 바뀌면 테스트가 검증할 행위 자체가
바뀌므로, 재구현 후 그 결과 동작을 zsh 테스트로 고정하는 순서가 자연스럽다.

## 의존 관계 요약

```
단계 1 PRD 작성(1.1) ─┬─→ 단계 1 push(1.3, 1.4) ──→ 단계 1 release(1.5) ──→ 단계 2 시작(2.1)
                       │
                       └─→ 단계 2 framework 가 PRD opt-out 파싱(2.3, 2.5)

단계 1 E2E(1.2) ─→ 단계 1 push(1.3): 머지 전 검증 완료가 권장(필수 아님)

단계 2 task 1~6(2.3) ─→ 단계 2 task 8 formula 검증(2.3): formula 검증은 tap repo
의 단계 1 push 후 (1.4) 의 변경이 origin 에 있어야 의미 있음. 단계 2.3 시작 전에
단계 1.4 가 완료되어 있어야 함.
```

핵심: **단계 1 의 push(1.3 + 1.4) 가 단계 2 의 모든 작업보다 앞선다.** 단계 2 의
CI 가 tap repo 를 anonymous clone 으로 검증하므로 tap 변경이 origin/main 에 없으면
formula 검증이 무의미하다.

## 결정 지점과 리스크

- **리스크 1**: 1.5 의 release-please PR 이 jg 의 버전을 어떻게 bump 할지 — 본
  세션에서 breaking change 마커(`refactor(jg)!:`) 를 의도적으로 제거했으므로
  major bump 는 발생하지 않는다(minor 또는 patch). 다만 release-please action
  의 동작은 origin 에 push 된 시점에 처음 검증 가능.
- **리스크 2**: 1.2 의 E2E 검증을 push 전후 어느 시점에 할지 — 본 roadmap 은
  push 전을 권장. push 후 E2E 에서 회귀가 발견되면 main 의 fix-forward 가 필요
  하므로 history 가 더 복잡해진다.
- **리스크 3 (해소됨)**: git-tidy 의 zsh 전용 검증 정책은 PRD 인터뷰에서 결정됐다.
  `bash_completion`·`bash_shell_integration`·`plugin_emits_main_commands`·
  `test_quality` 4개를 opt-out 하고, `unit_tests_exist`·`tests_execute_and_pass`
  는 zunit 같은 zsh 테스트 도구를 도입해 opt-in 으로 충족한다. zunit 도입은
  단계 4 의 작업이다.
- **결정 지점**: 단계 1 의 PRD 본문 작성 시점(push 전 / push 후 별 PR). 본
  roadmap 은 push 전 권장 — PRD 부재 상태로 push 하면 framework 도입 시
  소급 작성이 부담된다.

## 본 roadmap 의 완료 정의

다음 세 가지가 모두 참이면 본 roadmap 이 완료된 것으로 본다.

1. cli 와 tap 두 저장소의 `main` 이 origin 과 동기이며, jg/jgw 가 brew 와 로컬
   `mise run install` 양쪽에서 정상 동작.
2. `apps/<tool>/PRD.md` 3 개 모두 본문이 채워져 있고 품질 dimension 선언이
   opt-in/opt-out 으로 명시되어 있다.
3. PR CI 가 jg/totp/git-tidy 세 도구 모두에 대해 18 개 dimension 의 hard fail
   강제를 통과하며, 의도적 회귀가 자동으로 차단됨이 한 번 이상 확인된다.

## 본 roadmap 외 의도적으로 다루지 않는 것

- LLM 기반 의미적 평가(`single_source_no_drift` 의 자동 검증, 테스트 명명 평가
  등) — `single_source_no_drift` 는 원칙 항목으로만 유지.
- 정기 cron 재평가, 평가 점수 누적, 회귀 알림 봇.
- framework 자체에 대한 평가(dogfooding).
- 도구간 일관성의 의미적 검증(서로 다른 PRD 의 contradicting claims 등).
- tap repo 에 대한 자동 PR 생성.
